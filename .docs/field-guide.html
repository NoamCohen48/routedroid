Routedroid Field Guide

What the project does, what has been proven so far, what was deliberately left out, and where the work goes next. Written for someone who has never opened the repository.

The idea in one sentence

Plug an ordinary Android phone into a Linux PC with a USB cable, and the phone appears on your home network as if it had its own Ethernet cable: it gets its own IP address, other machines can reach it, and it can reach them. No rooting, no special firmware.

Whole IP packets travel unchanged from the LAN, through the PC's kernel, over the USB debug connection, into the phone's VPN interface — and back.

Four words you'll see everywhere

ADB
Android's USB debugging channel. It already carries a byte stream between PC and phone; we use it as a virtual network cable.
VpnService
The one Android API that lets a normal app receive and send raw IP packets. We don't run a real VPN; we use it as the phone's end of the cable.
TUN
The Linux equivalent: a virtual network interface (phone0) whose packets a program reads and writes. It is the PC's end of the cable.
Proxy ARP
The PC answering "who has the phone's IP?" on the LAN with its own hardware address, so the router sends the phone's traffic to the PC, which forwards it down the cable.

Why not just forward a few ports? Port forwarding turns the phone into a service behind the PC. Routedroid gives the phone a real address, so anything that works with a normal LAN host — pings, SSH into a terminal app, a web server on the phone, a game's LAN discovery — works without per-port setup.

Phase 0: proving it can work at all

Before writing the real product we listed every assumption that could sink it and tested each one on real hardware. The rule was strict: an assumption that fails is removed from the product, not papered over. Here is how each one came out.

  • PASS
    Packets survive the trip

    10 MB files copied both directions over USB with bit-exact checksums; ping, TCP and UDP all work; nothing leaks when the cable is yanked.

  • PASS
    Other machines can reach the phone

    A laptop on the router's Wi-Fi found the phone's address (via proxy ARP on the PC) and talked to it. The phone reached the router, the laptop, DNS and the Internet.

  • PASS
    The router will lend us a second address

    Over Ethernet the home router handed the PC a second DHCP lease for the phone, renewed it, and released it on exit — without disturbing the PC's own address.

  • PASS
    USB debugging keeps working while the VPN owns the phone's routes

    ~25 000 packets with adb shell, install and logcat unaffected.

  • PASS
    The secret handshake can't be spied on or faked

    The one-time secret reaches the phone through a protected channel (never on a command line), a hostile app on the same phone is denied at the OS level, wrong / replayed / expired secrets are refused, and the secret never appears in any log. Verified on Android 10 and 14.

  • PASS
    A crash never leaves the PC's network broken

    A small privileged helper applies every change (interface, firewall, sysctls, route) through a write-ahead journal. It was force-killed at all 37 possible points, on both a sandbox and real systemd; cleanup restored the PC to baseline every single time.

  • DROPPED
    One phone, several addresses at once

    Failed on every Android version: the phone always sends from its first address. So version 1 gives each phone one address on one chosen network. The architecture was simplified accordingly.

  • DEFERRED
    PC connected over Wi-Fi instead of Ethernet

    Not tested (no hardware at hand). Automatic address mode is therefore promised for Ethernet-attached PCs only; on Wi-Fi it's experimental and a doctor check tells you up front whether your access point cooperates. Manual static address always works.

  • DEFERRED
    Wireless (Wi-Fi) ADB instead of the USB cable

    Not tested (needs an Android 11+ phone). Version 1 is USB only; the tool refuses a network-attached phone with a clear message rather than risk cutting its own connection.

What exists today

Everything below is working code, but it is spike code: written to answer the questions above quickly, not to be shipped as-is.

Host tunnel (Rust)

phase0-tunnel: talks to the phone over ADB, does the authenticated handshake, moves packets between ADB and the TUN interface.

Privileged helper (Rust)

phase0-helper: the only part that runs as root. Journaled network changes, systemd-supervised cleanup, packet relay over a Unix socket.

Android app (Kotlin)

VpnService, protected bootstrap provider, mutual-HMAC handshake, packet pumps. Plus a deliberately hostile test app that tries to steal the secret (and fails).

Test rigs

Linux network-namespace labs that run without root, real-phone scripts (Samsung Android 10, emulator Android 14), the 37-point kill matrix, and a documented decision record for every gate.

The road ahead

The plan is six phases. Each turns one proven idea into a dependable feature. Phase 1 is built and verified on an emulator and a real phone; Phase 2 is next.

  • Phase 0 · doneFeasibility gates

    Every risky assumption tested on hardware; two deferred with reduced scope.

  • Phase 1 · doneRepository and protocol foundation

    Rebuild the spikes as real components: a proper CLI, a written wire-protocol spec with shared test fixtures for both Rust and Kotlin, session state machine, secure handshake, and an Android app with a basic status screen. Goal: one phone with a manually chosen address works end to end, cleanly.

  • Phase 2 · nextSafe host network configuration

    Move firewall, route and interface setup into the privileged helper for good, including coexistence with Docker and firewalld (both found on the real PC during Phase 0).

  • Phase 3Automatic DHCP

    The PC asks the router for the phone's address itself, renews it, and gives it back — transactionally, so a failure never leaves a half-configured network.

  • Phase 4Interface selection and egress policy

    Pick which PC network the phone joins; decide what happens when the PC's Internet route is elsewhere; handle cable unplug and reconnect.

  • Phase 5Helper hardening and recovery

    Lock down the root helper to a tiny typed API, reconcile state after crashes, and prove it under the full hardware matrix.

  • Phase 6User experience and packaging

    A doctor command that explains what's wrong, a phone UI that explains why it needs VPN permission, distro packages, reproducible APK, clean uninstall.

Phase 1, broken down

Phase 1 is where "it works on my desk" becomes "it works the same way every time". In the order we'll take it:

  1. Write the protocol down

    protocol/version-1.md: exact frame format, message types, size limits, and which messages are allowed in which state. Golden test files that both the Rust and Kotlin sides must pass.

  2. Host CLI skeleton

    The real routedroid binary: subcommands, structured logs, a clear error vocabulary, an ADB wrapper pinned to one phone with timeouts.

  3. Session state machine and handshake

    Port the Phase 0 state machine and mutual-HMAC handshake into the product, with tests for every illegal transition.

  4. Helper-owned TUN sessions

    The CLI never touches the network itself; it asks the helper over the sequenced-packet socket, exactly as the Phase 0 kill matrix proved safe.

  5. Android app foundation

    Foreground VPN service, permission flow, bootstrap provider, packet pumps, and a minimal status/stop screen.

  6. Acceptance

    One statically configured phone address end to end; both sides pass the same protocol fixtures; malformed input can't hang or bloat either side; stopping the VPN always closes the packet path.
